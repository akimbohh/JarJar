# JarJar — Data Contracts

Normative wire and storage formats. JSON Schemas in `schemas/` are the source of truth;
this document explains them and adds the SQL schema. All JSON is UTF-8; unknown fields
MUST be ignored by readers and MUST NOT be emitted by writers.

---

## 1. Conventions

- **Hashes:** SHA-256, lowercase hex, 64 chars. Field name is always `sha256`.
  (Registry-provided SHA-512/SHA-1 are used only to verify downloads; never stored in
  manifests.)
- **IDs:** `req_<ulid>` for requests, ULID lowercase (26 chars, Crockford base32).
  Player IDs: `plr_<ulid>`. Generated by the daemon only.
- **Timestamps:** RFC 3339 UTC with `Z`, e.g. `2026-08-05T17:04:05Z`. Field suffix `_at`.
- **Versions:** pack versions are consecutive positive integers `1, 2, 3, …` (field name
  `version` or `number` per schema). Version `N` is immutable once published. Git tag
  `v<N>` marks the commit that produced it. A rollback **creates a new version** whose
  content equals an older one — version numbers never decrease or fork.
- **Paths:** relative, forward slashes, no `.`/`..` segments, no leading slash. Allowed
  top-level segments in a pack: `mods/`, `config/`, `defaultconfigs/`, `kubejs/`,
  `scripts/`, `resourcepacks/`, `shaderpacks/`, `datapacks/`, plus the single files
  `server.properties` (server-side only) and files under `saves/` are **forbidden**.

## 2. Pack metadata — `jarjar.pack.json` (committed at pack repo root)

```json
{
  "schema_version": 1,
  "name": "Our Pack",
  "mc_version": "1.21.1",
  "loader": { "id": "neoforge", "version": "21.1.77" },
  "side_overrides": { "mods/somefile.jar": "client" },
  "curseforge_import": null
}
```

- `loader.id` ∈ `fabric | neoforge | forge | quilt`.
- `side_overrides` maps a manifest path to a forced side (`client|server|both`), taking
  precedence over registry metadata. Written by the importer or by hand; the pipeline
  never invents entries.

## 3. Mod lock — `mods.lock.json` (committed at pack repo root)

The authoritative list of jars in the pack (jars themselves are gitignored). One entry
per jar file:

```json
{
  "schema_version": 1,
  "mods": [
    {
      "path": "mods/sodium-fabric-0.6.0.jar",
      "sha256": "…64 hex…",
      "size": 123456,
      "side": "both",
      "source": {
        "platform": "modrinth",
        "project_id": "AANobbMI",
        "project_slug": "sodium",
        "version_id": "abcdEFgh",
        "download_url": "https://cdn.modrinth.com/…"
      }
    }
  ]
}
```

`source.platform` ∈ `modrinth | curseforge | manual`. For `curseforge`, use
`project_id` (mod ID, int as string) and `file_id` instead of `version_id`;
`manual` entries (files imported without registry provenance) carry only `download_url:
null`. `mods.lock.json` is written **only** by the executor and importer, never by the
model.

## 4. Version manifest — `schemas/manifest.schema.json`

One immutable JSON per published version, served at
`GET /api/v1/pack/manifests/{n}`. Built by the worker from the committed tree +
`mods.lock.json` + blob store.

Top-level shape (see schema for exact constraints):

```json
{
  "schema_version": 1,
  "pack": { "name": "...", "mc_version": "...", "loader": { "id": "...", "version": "..." } },
  "version": {
    "number": 42,
    "created_at": "…",
    "request_id": "req_…" ,
    "git_commit": "…40 hex…",
    "summary": "Added Sodium for better FPS.",
    "changelog": [ { "kind": "added_mod", "text": "Added Sodium 0.6.0" } ]
  },
  "files": [
    {
      "path": "mods/sodium-fabric-0.6.0.jar",
      "sha256": "…", "size": 123456,
      "side": "both", "kind": "mod"
    },
    { "path": "config/sodium-options.json", "sha256": "…", "size": 512, "side": "client", "kind": "config" }
  ]
}
```

Rules:

- `files` is the **complete** file set of the version (not a delta). Sorted by `path`
  ascending, byte-wise. Clients compute deltas by diffing two manifests.
- `side` semantics: clients install files with side ∈ {`client`, `both`}; the server
  apply step installs side ∈ {`server`, `both`}.
- `kind` ∈ `mod | config | script | resource | loader | other` — informational.
- Every `sha256` in `files` MUST exist in the daemon blob store before the manifest is
  published (config files are also stored as blobs at build time).
- `version.request_id` is `null` for imported (version 1) and rollback versions.

Side classification precedence (highest first):
1. `jarjar.pack.json.side_overrides`
2. Modrinth project `client_side`/`server_side` fields (`required|optional|unsupported`
   → `unsupported` on client ⇒ `server`; `unsupported` on server ⇒ `client`; else `both`)
3. `.mrpack` `env` field on import
4. Default `both`.

## 5. AI plan — `schemas/plan.schema.json`

The **only** structured artifact the model produces. Returned as headless structured
output (`--json-schema`, see `PIPELINE.md §4`) — the worker reads it from the
`structured_output` field of the Claude Code JSON result. The model also edits config
files directly in the worktree; the plan *records* those edits, it does not contain them.

```json
{
  "schema_version": 1,
  "status": "ok",
  "actions": [
    { "type": "add_mod", "platform": "modrinth", "project_id": "AANobbMI",
      "project_slug": "sodium", "version_id": "abcdEFgh", "reason": "Requested FPS mod" },
    { "type": "remove_mod", "path": "mods/old-mod-1.2.jar", "reason": "Replaced by X" },
    { "type": "update_mod", "platform": "modrinth", "project_id": "…",
      "from_path": "mods/foo-1.0.jar", "version_id": "…", "reason": "…" },
    { "type": "config_edit", "path": "config/mobspawns.toml",
      "description": "Halved zombie spawn weight from 100 to 50" },
    { "type": "server_property", "key": "view-distance", "value": "8" }
  ],
  "summary": "Slowed down mob spawns: zombie and skeleton spawn weights halved.",
  "admin_notes": "Only touched the two hostile-mob weights; passive mobs unchanged.",
  "confidence": "high",
  "clarification_question": null
}
```

- `status` ∈ `ok | needs_clarification | infeasible`.
  - `needs_clarification`: `actions` MUST be empty, `clarification_question` MUST be a
    non-empty string. The job pauses; the question is sent to the requesting player; the
    answer triggers a fresh planning run with the Q&A appended to the prompt.
  - `infeasible`: `actions` empty; `summary` explains why (e.g. no such mod for this
    MC version/loader). Job ends in status `infeasible`, not `failed`.
- `config_edit` entries MUST cover every file the model modified — the validator rejects
  the job if `git diff` shows a changed file with no corresponding `config_edit` action
  (and vice versa).
- `add_mod`/`update_mod` MUST carry version IDs that came from `jarjard modtool` output.
  The validator re-fetches each one from the registry; nonexistent or incompatible
  versions fail the job.
- `server_property` is the only mechanism for changing `server.properties` — the model
  must not edit that file directly (it is not present in the worktree).
- `confidence` ∈ `high | medium | low`. If `low`, the daemon forces the approval gate
  regardless of `require_approval` config.

## 6. Events — `schemas/events.schema.json`

Append-only, monotonically increasing `seq` (SQLite AUTOINCREMENT). Served via
`GET /api/v1/events?cursor=<seq>` long-poll (see `API.md`).

```json
{ "seq": 1041, "type": "version_published", "created_at": "…",
  "payload": { "version": 42, "summary": "Added Sodium for better FPS." } }
```

| `type` | `payload` |
|---|---|
| `version_published` | `{ "version": int, "summary": str }` |
| `request_updated` | `{ "request_id": str, "status": str, "player_name": str, "text": str, "question": str\|null, "error": str\|null, "version": int\|null }` |
| `server_status` | `{ "state": "running" \| "restarting" \| "down" }` |

Events older than 30 days may be pruned; clients recover from any gap by re-fetching
`/api/v1/pack/current` and recent requests (see `CLIENT.md §5`).

## 7. Daemon SQLite schema (normative DDL)

Database: `/var/lib/jarjar/db.sqlite`, WAL mode, `foreign_keys=ON`. Migrations are
numbered SQL files embedded in the binary (`internal/store/migrations/000N_*.sql`).

```sql
CREATE TABLE players (
  id          TEXT PRIMARY KEY,            -- plr_<ulid>
  name        TEXT NOT NULL UNIQUE,
  token_hash  TEXT NOT NULL UNIQUE,        -- hex(sha256(token))
  role        TEXT NOT NULL DEFAULT 'player' CHECK (role IN ('player','admin')),
  created_at  TEXT NOT NULL
);

CREATE TABLE invites (
  code        TEXT PRIMARY KEY,            -- 8 chars, crockford base32, upper
  role        TEXT NOT NULL DEFAULT 'player' CHECK (role IN ('player','admin')),
  created_at  TEXT NOT NULL,
  used_by     TEXT REFERENCES players(id)  -- null until redeemed; single-use
);

CREATE TABLE requests (
  id            TEXT PRIMARY KEY,          -- req_<ulid>
  player_id     TEXT NOT NULL REFERENCES players(id),
  text          TEXT NOT NULL,
  status        TEXT NOT NULL CHECK (status IN
                 ('queued','planning','awaiting_clarification','awaiting_approval',
                  'materializing','applying_server','published','failed','rejected','infeasible')),
  plan_json     TEXT,                      -- validated plan (schemas/plan.schema.json)
  clarification_question TEXT,
  clarification_answer   TEXT,
  error         TEXT,                      -- human-readable failure cause
  version       INTEGER,                   -- produced pack version, once published
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

CREATE TABLE versions (
  number      INTEGER PRIMARY KEY,         -- 1, 2, 3, …
  created_at  TEXT NOT NULL,
  request_id  TEXT REFERENCES requests(id),
  git_commit  TEXT NOT NULL,
  summary     TEXT NOT NULL,
  status      TEXT NOT NULL CHECK (status IN ('published','superseded')),
  manifest_path TEXT NOT NULL              -- /var/lib/jarjar/manifests/<n>.json
);

CREATE TABLE events (
  seq         INTEGER PRIMARY KEY AUTOINCREMENT,
  type        TEXT NOT NULL,
  payload     TEXT NOT NULL,               -- JSON
  created_at  TEXT NOT NULL
);
```

Status transitions for `requests` (only these; enforced in `internal/jobs`):

```
queued → planning
planning → awaiting_clarification | awaiting_approval | materializing | infeasible | failed
awaiting_clarification → planning            (on player answer)
awaiting_approval → materializing | rejected (admin decision)
materializing → applying_server | failed
applying_server → published | failed         (failed here triggers server rollback)
```

Write discipline: `jarjard serve` owns all tables; `jarjard worker` writes only
`requests` (its own row), `versions`, and `events`, always through `internal/store`
helpers. SQLite WAL makes the two-process access safe; busy_timeout = 5000 ms.

## 8. Client local state — `schemas/client-state.schema.json`

`<data>/state.json`, written atomically (temp file + rename) after every successful
apply:

```json
{
  "schema_version": 1,
  "applied_version": 42,
  "files": {
    "mods/sodium-fabric-0.6.0.jar": { "sha256": "…", "size": 123456, "mtime_ms": 1730000000000 }
  }
}
```

`files` caches the hash of every managed file as last applied. On sync, a file whose
`size` and `mtime_ms` match the cache is trusted without re-hashing; otherwise it is
re-hashed. Files present in `instance/` but absent from both the cache and the target
manifest are left untouched (player-added extras like screenshots, saves, options.txt
are never deleted); files that were in the *previous* manifest but not the new one are
deleted on apply.

`<data>/config.json`: `{ "schema_version": 1, "server_url": "https://…", "token": "…",
"player_name": "…", "minecraft_dir": null, "autostart": true }` — `minecraft_dir`
overrides the platform-default `.minecraft` location for launcher integration.
